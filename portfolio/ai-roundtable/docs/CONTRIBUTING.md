# コントリビューションガイド

一人開発でも守れる最小限のルールです。AIは [AI_GUIDE](AI_GUIDE.md) も確認してください。

## 開発環境

READMEの手順で仮想環境と依存関係を準備し、`python -m pytest tests` で確認します。ツールを追加する場合は設定をリポジトリで共有します。

## コーディング規約

- PythonはPEP 8、公開関数と境界データには型ヒント
- 関数、クラス、モジュールは明確な単一責任
- DRY、KISS、YAGNIを優先
- コメントは処理内容より判断理由や制約
- ルート関数から外部API処理を分離
- 利用者向けエラーと安全な内部診断を分離

### 命名

- Python変数・関数・モジュール: `snake_case`
- Pythonクラス: `PascalCase`
- 定数・環境変数: `UPPER_SNAKE_CASE`
- JavaScript: `camelCase`
- CSS・URL: `kebab-case`
- テスト: `test_<expected_behavior>`

名前は英語で役割を表し、不要な略語を避けます。

## テスト方針

- 新機能とバグ修正には成功・境界値・失敗のテストを追加
- 外部AIは通常モックし、課金と不安定性をテストへ持ち込まない
- 実APIテストは明示的に分離し、秘密情報と費用を管理
- PR前に対象テストを実行し、未実行項目を明記

## Gitとブランチ

- `main`: 常に動く状態
- `feature/<topic>`、`fix/<topic>`、`docs/<topic>`、`chore/<topic>`: 短命ブランチ
- `develop`: 複数変更を統合する必要が生じた場合だけ利用

一人開発中も小さなコミットを保ち、強制pushや履歴書き換えは共同作業者への影響を確認します。

## コミットメッセージ

```text
<type>: <簡潔な要約>
```

`feat`、`fix`、`docs`、`test`、`refactor`、`chore` を使います。必要なら本文へ「なぜ」と影響を書きます。無関係な変更を混在させません。

## Pull Requestとレビュー

PRには目的、変更内容、確認方法・結果、画面変更、仕様・安全・費用への影響、残る課題を記載します。レビューでは次を確認します。

1. 仕様とMVPへの適合
2. 秘密情報、プライバシー、API費用、データ損失のリスク
3. 可読性、責務、過剰設計
4. 成功・失敗テスト
5. 文書と変更履歴

重大な安全問題や無制限課金の可能性はマージを止めます。

## 文書と秘密情報

仕様、設計、操作、判断が変わる変更は同じPRで正本文書とCHANGELOGを更新します。APIキー、`.env`、認証情報、実ユーザーデータをコミットしません。

## 依存関係

新規ライブラリには、解決する課題、既存手段で代替できない理由、保守状況、ライセンス、セキュリティ、サイズへの影響を説明します。
