# 設計判断記録

## 記録方法

重要な判断には連番を付け、次の項目を記録します。

- 日付
- 状態: proposed / accepted / superseded / rejected
- 背景
- 決定内容と理由
- 検討した代替案
- メリットとデメリット
- 将来見直す条件

記録は過去を書き換えて正当化せず、変更時は新しい判断から旧判断を参照します。現段階では1ファイルで管理し、件数が増えたら `docs/decisions/NNNN-title.md` へ分割します。

## ADR-001: Webアプリを採用

- 日付: 2026-07-18
- 状態: accepted
- 背景: ブラウザから質問し、複数AIの回答を比較したい
- 決定: Webアプリとして構築する
- 理由: 端末への導入負担が小さく、将来の共有・モバイル対応へ発展しやすい
- 代替案: CLI、デスクトップ、ネイティブモバイル
- メリット: 利用しやすく配布しやすい
- デメリット: Webセキュリティと公開運用が必要
- 見直し条件: オフライン・端末固有機能が主要要件になる

## ADR-002: PythonとFastAPIを採用

- 日付: 2026-07-18
- 状態: accepted
- 背景: AI APIを扱う型付きHTTPバックエンドが必要
- 決定: PythonとFastAPIを使う
- 理由: AI関連SDKとの親和性、型検証、非同期処理、OpenAPI
- 代替案: Flask、Django、Node.js
- メリット: MVPを小さく開始でき、テストしやすい
- デメリット: 運用・非同期処理の理解が必要
- 見直し条件: 性能・組織要件を満たせない実測が得られる

## ADR-003: MVP UIはHTML・CSS・JavaScript

- 日付: 2026-07-18
- 状態: accepted
- 背景: 質問フォームと回答表示が中心
- 決定: Jinja2を含む標準Web技術で開始する
- 理由: ビルド環境と依存を増やさずMVPへ集中できる
- 代替案: React、Vueなど
- メリット: 単純で保守しやすい
- デメリット: 高度な画面状態では複雑化しうる
- 見直し条件: UI状態と再利用部品が明確に増える

## ADR-004: APIキーは `.env` で管理

- 日付: 2026-07-18
- 状態: accepted
- 背景: 秘密情報をコードと分離する必要がある
- 決定: ローカルはGit管理外の `.env`、本番は秘密情報管理機能を使う
- 理由: 漏洩リスクを下げ、環境別設定を分離できる
- 代替案: コード埋め込み（却下）、OS環境変数のみ
- メリット: ローカル開発が容易
- デメリット: ファイル管理と漏洩時対応が必要
- 見直し条件: 管理基盤導入時も原則は維持し、保存先だけ変更する

## ADR-005: OpenAIから段階的に接続

- 日付: 2026-07-18
- 状態: accepted
- 背景: 最初から3社を実装すると障害原因と共通境界が不明瞭になる
- 決定: OpenAI、Gemini、Claudeの順で接続する
- 理由: 1社で通信・失敗・テストを確立してから共通化する
- 代替案: 3社同時実装
- メリット: 小さく検証できる
- デメリット: 一時的に比較機能が完成しない
- 見直し条件: API提供状況や優先プロバイダーが変わる

## ADR-006: 外部AIプロバイダーを分離

- 日付: 2026-07-18
- 状態: accepted
- 背景: SDK、モデル、エラー、利用量が各社で異なる
- 決定: 差異をサービス・アダプター境界へ局所化する
- 理由: 追加・変更・テストを他層へ波及させにくい
- 代替案: ルート関数からSDKを直接呼ぶ
- メリット: 交換可能性とテスト容易性
- デメリット: 小さな抽象化コスト
- 見直し条件: 実装で共通契約が不自然と判明する

## ADR-007: 多数決を正解としない

- 日付: 2026-07-18
- 状態: accepted
- 背景: 複数モデルは同じ誤情報や偏りを共有しうる
- 決定: 一致数ではなく根拠、独立性、不確実性、反証を評価する
- 理由: 人間の意思決定支援という理念に合う
- 代替案: 単純多数決
- メリット: 説明可能で慎重な比較
- デメリット: 評価処理が複雑になりうる
- 見直し条件: 原則は維持し、具体的評価方法は検証結果で更新する
